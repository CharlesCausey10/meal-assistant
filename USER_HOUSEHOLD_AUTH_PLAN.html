Implementation Plan

Meal Assistant User, Household, and WorkOS Migration Plan

This document captures the agreed direction for adding users, households, WorkOS authentication, household-shared meals/logs/grocery lists, copied starter ingredients, empty starting meal libraries, and user-specific meal preferences. It is intended to give future agents enough context to implement the migration without needing the original conversation.

Current App Context

Meal Assistant is currently a personal Next.js App Router application backed by Prisma and PostgreSQL. The current data model has no user or household concept. Existing rows represent the owner/developer's personal dev data.

Before making implementation changes, read PROJECT_STRUCTURE.md. It describes the app structure, major files, Prisma models, server actions, and query locations.

Important: The existing database contains personal dev data. If a future agent creates test households, users, logs, meals, grocery lists, or ingredients while testing locally, those records must be cleaned up afterward.

Decisions Already Made

  • Use WorkOS AuthKit for authentication.
  • Use WorkOS Organizations as the auth-side representation of households.
  • Keep local app tables as the source of truth for meal, ingredient, log, and grocery data.
  • Do not add a scope column to Ingredient or Meal.
  • Use Ingredient.householdId = null to mean a global default ingredient row.
  • Do not maintain global/default starter meals for onboarding. New households start with no meals and add meals manually or copy opted-in templates from Discover.
  • Use householdId != null to mean a row owned by one household.
  • When a household is created, copy all global ingredients into that household.
  • Copied meals do not need sourceMealId.
  • Do not add household ingredient preferences.
  • Meal preferences are user-specific 1-10 integer scores.
  • Household members share meals, logs, leftovers, grocery lists, and ingredients.
  • The only household-member-specific food signal is meal preference, used for dashboard suggestions.
  • Discover sharing is a household-level tri-state: null means undecided, true means opted in, and false means private.

Execution Notes

Phase 1 adjustment: the first implementation pass adds the new identity and household schema while keeping Meal.preference temporarily. That allows the app to continue running before a real WorkOS user exists. After WorkOS is configured and the initial owner user is known, migrate existing Meal.preference values into MealPreference for that user, then remove Meal.preference.
User action checkpoint: before the WorkOS integration can be finished, the owner needs to create or choose a WorkOS account/application and provide local environment values for WORKOS_API_KEY, WORKOS_CLIENT_ID, WORKOS_COOKIE_PASSWORD, and NEXT_PUBLIC_WORKOS_REDIRECT_URI. Do not invent placeholder secrets.
Verification preference: do not personally open or verify the local dev server. When localhost verification is needed, ask the owner to run/check the app instead.
Production preflight finding: the current database is also the production database. A read-only preflight on June 10, 2026 found 63 meals, 232 ingredients, 0 meal logs, and 3 grocery lists. Ingredient names had no case-insensitive duplicates. Meal names had these case-insensitive duplicates: almond butter toast, bbq chicken, cereal, nutella toast, turkey sandwich, and yogurt. Because of this, Phase 1 intentionally does not add meal-name unique indexes. Meal-name uniqueness remains the target invariant after the future tag/multi-category cleanup.
Phase 1 applied: on June 10, 2026, migration 20260610120000_add_users_households_phase1 was applied to the production-backed Neon PostgreSQL database. A post-migration read-only check found 1 household, 0 users, 0 household members, 63 household-linked meals, 232 household-linked ingredients, 3 household-linked grocery lists, 0 household-linked meal logs, and 0 meal preferences. The existing data is now attached to Personal Household; WorkOS users/memberships have not been created yet.
Auth integration started: WorkOS AuthKit Next.js package @workos-inc/authkit-nextjs was installed and the app now has proxy.ts, app/login/route.ts, app/callback/route.ts, app/logout/route.ts, and lib/auth.ts. The root page requires sign-in and server-rendered app data is scoped to the authenticated household. For bootstrapping, the first signed-in WorkOS user is linked as OWNER of Personal Household when no WorkOS organization context exists.
Auth runtime fix: do not call getSignInUrl() or withAuth({ ensureSignedIn: true }) from server components/actions in this app, because the WorkOS PKCE cookie must be set from a route handler or proxy context. Server components/actions should redirect to local /login; app/login/route.ts then calls getSignInUrl(). proxy.ts enables middlewareAuth and leaves /login and /callback unauthenticated.
Meal preference migration applied: on June 10, 2026, migration 20260610133000_migrate_meal_preferences_to_users moved the 63 existing meal scores from Meal.preference into MealPreference for the owner of Personal Household, then dropped Meal.preference. A post-migration read-only check found 63 MealPreference rows, all with valid 1-10 scores, and confirmed the old Meal.preference column no longer exists.
Meal query runtime fix: after the preference migration, Prisma errored on the Meals tab when relation-loading preferences with both where: { userId } and take: 1. Because MealPreference is unique by (userId, mealId), take: 1 is unnecessary. It was removed from meal, dashboard, and grocery meal queries.
Navigation performance and sign-out fix: the root page now renders only the active tab's server component instead of constructing every tab on each request. PageLayout now forwards userEmail and householdName correctly, which restores the account strip and Sign out link. Auth context lookup also avoids repeated user/membership upserts when the local records already exist.
Household management status: app/households/page.tsx and app/actions-households.ts now enforce one local household membership per user. The page is singular, with owner-driven actions to link Personal Household to a WorkOS Organization, manage invite links, remove members, and let non-owner members leave into a new personal household with copied meals and ingredients. Owners do not see this copy flow because they already control their household.
Invite and auto-household migration: households now have one active app-level invite token. Owners can create the first invite link, copy an existing link, refresh the token, and see a snackbar confirmation when a link is copied or refreshed-and-copied. Invite acceptance moves the accepting user out of their current household, deletes their old household only when it becomes empty, creates a WorkOS organization membership and local HouseholdMember, then refreshes the session into that household. Uninvited first-time users who sign in directly are automatically given their own WorkOS-backed household.
One-household rule: HouseholdMember.userId is unique. A user can be in exactly one household at a time. WorkOS Organizations still exist behind the scenes, but the product model is "your household", not a multi-household workspace switcher.
WorkOS membership cleanup hardening: household transition paths now prune extra WorkOS Organization memberships for the affected user after successful local membership moves. This keeps WorkOS aligned with the app-level one-household rule when a user accepts an invite, leaves into a copied household, is removed into a personal household, links an existing household to WorkOS, or returns through the auth callback.
Cross-household mutation hardening: meal create/edit now validates submitted ingredient IDs against the authenticated household before creating MealIngredient rows. Adding a meal to a grocery list now validates both the list and meal belong to the current household before writing GroceryListMeal. The ingredients API now returns JSON 401 responses for unauthenticated requests and validates category values against the Prisma enum.
Starter meal picker removed: new households now start with no meals. They can create meals manually or copy opted-in meal templates from Discover. Global/default rows are still useful for ingredients, but not for meals.
Discover consent status: households now have a nullable discoverableMealsOptIn setting. Owners can choose Allow Discover or Keep private from the Household page. The Discover tab now lists meal templates from other opted-in households and lets the current household copy selected meals.
Production readiness checkpoint: as of June 11, 2026, the core user/household migration is functionally complete locally: WorkOS sign-in works, one-household membership is enforced, invite/member management works, member leave/copy works, Discover opt-in/copy works, and all main tabs are household scoped. This is a reasonable stopping point to publish the code and configure production WorkOS credentials, after a final local smoke test and production environment setup.
Production WorkOS relink fix: staging and production WorkOS environments can issue different workosUserId values for the same Google account. Because the local database is shared between local testing and production, lib/auth.ts now relinks an existing local User by email when the WorkOS ID changes instead of failing on the unique email constraint.
Meal category tagging applied: migration 20260611140000_add_meal_categories added MealCategory, backfilled every existing meal from its current Meal.category, and updated meal create/edit/filter/dashboard, Discover, grocery, and copy flows to preserve and use multiple meal-window tags. The legacy Meal.category column remains as the primary/backward-compatible category.
Meal-name uniqueness applied: on June 12, 2026, migration 20260612100000_unique_meal_names_per_household added raw SQL partial expression indexes that enforce unique meal names per household after lower(trim(name)) normalization, plus the same normalization for global meals where householdId IS NULL. The migration required deleting one duplicate bbq chicken row and one duplicate nutella toast row from the shared production-backed database after the owner approved deleting either duplicate record. Meal create/edit actions now return a friendly inline error instead of surfacing a Prisma unique constraint exception.

Target Data Model

The app has introduced local User, Household, HouseholdMember, and MealPreference models. Existing operational models are household-scoped.

New Models

enum HouseholdRole {
  OWNER
  MEMBER
}

model User {
  id            Int                @id @default(autoincrement())
  workosUserId  String             @unique
  email         String             @unique
  firstName     String?
  lastName      String?
  memberships   HouseholdMember[]
  preferences   MealPreference[]
  createdAt     DateTime           @default(now())
  updatedAt     DateTime           @updatedAt
}

model Household {
  id                   Int                @id @default(autoincrement())
  workosOrganizationId  String?            @unique
  discoverableMealsOptIn Boolean?
  name                 String
  members              HouseholdMember[]
  meals                Meal[]
  ingredients          Ingredient[]
  mealLogs             MealLog[]
  groceryLists         GroceryList[]
  createdAt            DateTime           @default(now())
  updatedAt            DateTime           @updatedAt
}

model HouseholdMember {
  id           Int           @id @default(autoincrement())
  householdId  Int
  userId       Int
  role         HouseholdRole @default(MEMBER)
  household    Household     @relation(fields: [householdId], references: [id], onDelete: Cascade)
  user         User          @relation(fields: [userId], references: [id], onDelete: Cascade)
  createdAt    DateTime      @default(now())
  updatedAt    DateTime      @updatedAt

  @@unique([householdId, userId])
}

model MealPreference {
  id        Int      @id @default(autoincrement())
  userId    Int
  mealId    Int
  score     Int
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  meal      Meal     @relation(fields: [mealId], references: [id], onDelete: Cascade)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([userId, mealId])
}

Database Constraints

Because uniqueness with nullable columns can be awkward in PostgreSQL and Prisma, use raw SQL partial unique indexes for global versus household-owned names. 

CREATE UNIQUE INDEX ingredient_global_name_unique
ON "Ingredient"(lower("name"))
WHERE "householdId" IS NULL;

CREATE UNIQUE INDEX ingredient_household_name_unique
ON "Ingredient"("householdId", lower("name"))
WHERE "householdId" IS NOT NULL;

CREATE UNIQUE INDEX meal_global_name_unique
ON "Meal"(lower("name"))
WHERE "householdId" IS NULL;

CREATE UNIQUE INDEX meal_household_name_unique
ON "Meal"("householdId", lower("name"))
WHERE "householdId" IS NOT NULL;

ALTER TABLE "MealPreference"
ADD CONSTRAINT meal_preference_score_check CHECK ("score" BETWEEN 1 AND 10);
Phase 1 constraint decision: ingredient uniqueness remains enforced with partial global/household indexes. Meal-name uniqueness is postponed because existing duplicate meal names represent meals that can be used in multiple meal windows.

Household Creation Flow

  1. User signs in through WorkOS AuthKit.
  2. App calls withAuth({ ensureSignedIn: true }).
  3. App upserts local User from the WorkOS session user.
  4. App checks whether the user already has one local household membership.
  5. If none exists and the user signed in directly, app automatically creates a personal WorkOS Organization and local household.
  6. If the user joins an invite, app moves them into the invited household and out of any previous household.
  7. When creating a personal household, create the WorkOS Organization.
  8. Create the WorkOS organization membership for the current user.
  9. Create local Household with workosOrganizationId.
  10. Create local HouseholdMember with role OWNER.
  11. Copy all global ingredients where householdId IS NULL into the new household.
  12. Start the household with an empty meal library; the user can add meals manually or use Discover.

New Household Meal Startup

  1. Copy global default ingredients where Ingredient.householdId IS NULL.
  2. Do not copy or present global/default meals during onboarding.
  3. Show an empty meal library until the household creates meals manually or copies opted-in templates from Discover.
This keeps the app from imposing a default taste profile. Ingredients are a useful catalog bootstrap; meals are personal enough that they should come from the household or from explicit Discover copies.
Do not keep a sourceMealId. Once a meal is copied from Discover, the household meal is its own editable row.

Invite Flow

  1. Household owner clicks Create link when no invite link exists.
  2. The app creates the household invite token, immediately copies the invite URL to the clipboard, and shows a snackbar confirmation.
  3. Household owner can send the copied URL by text, email, or any other channel.
  4. Once a link exists, the UI shows separate Refresh and Copy buttons.
  5. Clicking Copy copies the current invite URL and shows a snackbar confirmation.
  6. Clicking Refresh rotates the token, immediately copies the new URL, and shows a snackbar confirmation.
  7. Invitee opens the app-level invite URL, then signs up or signs in through WorkOS if needed.
  8. Invitee accepts the invite in the app.
  9. If the invitee owns a household with other members, app blocks the join until those members are removed.
  10. If the invitee's old household becomes empty, app deletes that old local household and WorkOS Organization.
  11. App creates the WorkOS organization membership, upserts local User, creates local HouseholdMember, and refreshes the session into that household.

Leave Household Flow

  1. Only non-owner members see Leave household on the Household page.
  2. Clicking Leave household opens a confirmation modal.
  3. The modal has a pre-checked option to copy meals, ingredients, and the user's meal preference scores.
  4. The modal has a second pre-checked option to copy the meal log so dashboard recommendations can continue from cooked history.
  5. The meal-log checkbox is only checkable when the meals/ingredients/preferences checkbox is checked.
  6. App creates a new WorkOS Organization and personal local household for that user using an internal default name.
  7. If selected, app copies the current household's ingredients, meals, and user preference scores into the new household.
  8. If selected, app copies meal-log rows into the new household and rewires meal-linked logs to the copied meals.
  9. The copy implementation should bulk-insert ingredients, meal ingredients, preferences, and logs so it does not exceed Prisma's interactive transaction timeout.
  10. If copying fails before the membership move, app deletes the newly created local household and WorkOS Organization.
  11. App removes the user from the old household.
  12. Owners cannot use this flow because they already control their household and can edit meals and ingredients directly.

Discover Privacy Plan

  1. Discover is opt-in per household, controlled by Household.discoverableMealsOptIn.
  2. null means the household owner has not decided yet.
  3. true means household meal templates may appear in Discover.
  4. false means household meals remain private and excluded from Discover.
  5. Discover must not expose meal logs, grocery lists, household names, member names, or per-user preference scores.
  6. Discover suggestions should track seen meal IDs in browser localStorage, per user/device/browser.
  7. Seen meal IDs should expire after 30 days, so meals can eventually reappear.
  8. Do not create database records for passive impressions, swipes, or dismissals.
  9. Persist only meaningful actions such as copying/saving a discovered meal into a household.

Discover Implementation Status

  • app/discover-tab.tsx fetches up to 100 meal templates from other households where discoverableMealsOptIn = true.
  • The Discover query excludes meals whose names already exist in the current household.
  • The Discover empty state distinguishes no opted-in meals, all shared meals already existing by name in the current household, and all current suggestions being hidden in this browser.
  • app/discover-content.tsx stores hidden/copied suggestion IDs in browser localStorage with a 30-day expiration, keyed by local user ID.
  • app/actions-discover.ts validates the source household is still opted in before copying a meal.
  • Copying a discovered meal copies only that meal and the ingredients used by that meal; it does not copy the source household's full ingredient catalog, logs, grocery lists, household name, member names, or preferences.

Query and Mutation Rules

Meals

Normal app views should query only Meal rows for the current household.

There is no starter meal picker; global meals are not used for onboarding.

Ingredients

Normal ingredient autocomplete and CRUD should use the current household's copied ingredients.

Global ingredients are seed/template data, not normal editable app data.

Meal Logs

Meal logs and active leftovers must include householdId and query only the current household.

Grocery Lists

Grocery lists and grocery items are household-owned. All list queries and actions must enforce current household access.

Dashboard

Dashboard suggestions should use household meals/logs plus the current user's MealPreference scores.

Server Actions

Every mutation should derive userId and householdId from the signed-in WorkOS session, never from hidden form fields alone.
